## 1. 协作概况

### 1.1 这个作业本身要做什么

用文件 IO 做两件在 Linux 上很「底层」的事，并把它们拼成一个能用的工具：

| 作业要求 | 我用到的系统调用 | 落地位置 |
| --- | --- | --- |
| 生成空洞文件，逻辑 ≥128KB，未写入区不占磁盘块 | `open(O_CREAT)` + `ftruncate()`；失败回退 `lseek(size-1)` + `write` + `ftruncate` | `src/sio_sparse.c` → `sio_create_sparse()` |
| `lseek` + `write` 定点写入，不破坏其余空洞 | `pwrite()` / `pread()`（自带偏移，不动文件偏移量） | `src/sio_util.c` → `sio_pwrite_full()` / `sio_pread_full()` |
| 记录已完成偏移，Ctrl-C 后从断点继续 | sidecar 位图 `<target>.sio`，`fsync(file)` → 置位 → `fsync(tmp)` → `rename` → `fsync(dir)` | `src/sio_bitmap.c` → `sio_map_save()`；`src/sio_main.c` → `cmd_write()` |
| 打印逻辑大小 / 实际占用块数 / 空洞占比 | `stat()` 的 `st_size` 与 `st_blocks`（`st_blocks × 512` = 实际占用字节） | `src/sio_sparse.c` → `sio_stat_path()`、`sio_hole_ratio()` |

- `verify` 子命令：已提交的块逐块回读并与数据源比对；未提交的块必须**逐字节都是 `0x00`**（证明空洞真的没被破坏，而不是「看起来像」）；
- HTTP Range 数据源（`file://` 用于离线复现，`http://` 用于真实下载场景），因为「下载器」不接真实的远端数据源，断点续传就只是个本地文件搬运游戏。

## 2. Prompt 记录（9 条主要协作）

### Prompt 1 —— 技术路线：为什么是 `ftruncate` 而不是写零填充

```
我要写一个 C 命令行工具做「空洞文件 + 断点续传下载器」，只用 POSIX/libc，不要第三方库。
第一步就把我最犹豫的地方定下来：要造一个逻辑 8MiB、但磁盘上先不占空间的「空洞文件」，
我有三种想法：
  (a) open 之后 ftruncate(fd, 8M)
  (b) open 之后 lseek 到 8M-1 写 1 个字节，再 ftruncate 回 8M
  (c) 老老实实 write 8MiB 的 0x00 进去
请从文件系统层面说明这三种做法在 ext4 上分别会让 inode 变成什么样，
stat 出来的 st_size 和 st_blocks 各是多少，读空洞区间时内核返回什么，
以及为什么 (c) 不能用来实现「空洞文件」。另外告诉我 ftruncate 什么时候会失败。
```

**AI 回复要点**：

- (a) 是最干净的做法：`ftruncate` 只改 inode 的 `i_size`，**不分配任何数据块**，`st_size=8MiB`、`st_blocks=0`、`du` 显示 0；
- (b) 效果等价，但会实打实分配 1 个数据块（ext4 上 4KiB），因为它确实写了一个字节；
- (c) 直接把每一页都写实了，`st_blocks` 会等于逻辑大小，`du` 8MiB——**这不是空洞文件，只是「内容恰好是 0 的普通文件」**，作业要求直接失效；
- 读空洞区间时内核不查数据块，直接返回零页，所以 `pread` 得到全 `0x00`、不产生磁盘 IO；
- `ftruncate` 可能失败：超过 `RLIMIT_FSIZE`、超过文件系统单文件上限、只读 FS、`O_APPEND` 之外的非常规 fd 等。

**我的判断**：**采纳**，但保留 (b) 作为回退路径。

**理由与落地**：AI 的解释和 `man 2 ftruncate`、`man 2 stat` 一致，我在虚拟机里用
`stat -c '%s %b'` 和 `du` 复核过（`ftruncate` 后 `%b=0`）。
唯一我加的是：不把 `ftruncate` 当唯一路径，因为它在某些受限环境会失败，
失败时如果直接报错退出，作业的「最小可用」就挂了。所以落地为两级：
首选 `ftruncate`，失败则告警 + 走 (b) 回退 + 明确打印「磁盘占用会多 1 个数据块」，
绝不静默降级。代码在 `src/sio_sparse.c` 的 `sio_create_sparse()`（第 66–93 行的 `if (ftruncate(...) != 0)` 分支）。

### Prompt 2 —— 进度存档：位图放哪、怎么保证「位图不撒谎」

```
进度信息我决定存成一个 sidecar 文件（默认 <target>.sio），但有两个问题必须说清楚：

1) 你在上一轮建议过「存一个 last_offset，表示已经连续下到哪了」，我拒绝这个方案：
   只要下载顺序不是严格递增（某块重试、跳块、或者将来做并发），last_offset 就表达不了
   「中间某块已完成、两边还没下」的状态，续传时会重下甚至漏块。请改成能表达任意块状态的方案。

2) 更关键的是顺序问题。请你按「写一块数据」的完整生命周期，把下面这些动作排一个顺序，
   并对每一步说明「如果恰好在这一步之后掉电 / kill -9，会发生什么」：
   写数据、回读校验、fsync(目标文件)、位图置位、fsync(位图)、rename(位图)。
   我要的保证是：任何时刻崩溃后重启，都不允许出现「位图说这块完成了，但磁盘上这块数据是错的」。
   宁可重下一块，也不许静默跳过一块错数据。还有：位图本身怎么做原子替换？
```

**AI 回复要点**：改成定长块 + 位图（bitmap），每块 1 bit；给出顺序
`写数据 → 回读校验 → 位图置位 → fsync → rename`；
并指出 `rename()` 在同文件系统内是原子替换，因此位图「要么是旧的完整版，要么是新的完整版」。
掉电分析里也承认：如果把置位放在 `fsync(数据)` 之前，可能出现「账记了、数据没落盘」。

**我的判断**：**位图方案采纳，提交顺序部分采纳并改写。**

**理由与落地**：位图能表达任意块状态，这是硬需求，采纳。
但 AI 给的顺序里 `fsync(目标文件)` 的位置是**可选的、靠后的**，我把它提前并变成动作的必经一环：

```
pwrite 数据 → pread 回读比对 → fsync(目标文件) → 位图置位 → 写 .tmp → fsync(.tmp) → rename()
```

理由是这两种失败的代价完全不对称：

| 崩溃点 | 后果 | 是否可接受 |
| --- | --- | --- |
| 数据已落盘、位图没记上 | 下次重下这一块，`pwrite` 幂等，结果仍然正确 | ✅ 可接受（只是浪费一次 IO） |
| 位图记了、数据没落盘 | 续传永远跳过这一块，得到一段**没人发现的错数据** | ❌ 静默数据损坏，绝不可接受 |

代码落在 `src/sio_main.c` 的 `cmd_write()` 循环体内（`sio_map_set()` + `sio_map_save()` + `fsync(fd)` 的先后），
原子替换落在 `src/sio_bitmap.c` 的 `sio_map_save()`（先写 `<path>.tmp` 再 `rename`）。

### Prompt 3 —— 信号处理：为什么故意不加 `SA_RESTART`

```
继续问信号这块。Ctrl-C 要求的效果是「立刻在块边界干净退出，并保留断点」。
我打算 sigaction 时 sa_flags = 0（不加 SA_RESTART），处理函数里只置一个 sig_atomic_t 标志，
不做任何别的事。请帮我确认两件事：

1) 不加 SA_RESTART 到底意味着什么？我按 Ctrl-C 时，正在阻塞的 pread()/recv() 会返回什么？
   如果加了 SA_RESTART，行为有什么不同？
2) 在信号处理函数里为什么不能做日志打印、free、或者直接 exit()？我如果就是想「立刻退出」呢？
   还有个副作用我没想明白：不加 SA_RESTART 之后，那些因为 EINTR 提前返回的系统调用，
   会不会被我自己的重试逻辑当成「真的失败了」？
```

**AI 回复要点**：

- 不加 `SA_RESTART` 时，被信号打断的阻塞系统调用返回 `-1` 且 `errno == EINTR`；加了之后内核自动重启该调用，`read`/`write` 会「悄悄续上」，从用户态看不出来被打断过；
- 处理函数里只能碰 `volatile sig_atomic_t`；`printf`/`malloc`/`free` 都不是异步信号安全的（可能死锁在已持有的锁上），`exit()` 会跑 `atexit`/flush 缓冲，属于未定义行为区；
- 处理函数里 `exit()` 的最大问题是：可能死在 `pwrite` 中途，留下写了一半的块和没记账的位图；
- 最后 AI 承认：EINTR 确实会和重试逻辑打架，建议「在重试循环里遇到 EINTR 且标志已置位就直接放弃」。

**我的判断**：**采纳**（AI 承认的那条副作用我自己实测复现后，按我的方式修）。

**理由与落地**：`sa_flags = 0` 是为了让阻塞中的 `pread`/`recv` **能被叫醒**，
否则用户按了 Ctrl-C 却要等当前块读完才反应，「Ctrl-C 没反应」是体感最差的一类 bug。
处理函数只置标志，落在 `src/sio_util.c` 的 `on_signal()` 与 `sio_install_signal_handlers()`。

AI 关于 EINTR 的那条提醒是对的，但它的修法（在重试循环里判断）我不满意——
那还是「先失败、再判断」，日志上会多出一堆误导性的「读取失败（第 1 次）」。
我改成**每块开始前先看一次中断标志**（`sio_interrupted()`），
用户按下 Ctrl-C 后，最多等当前块提交完就在块边界干净退出，一条假的失败日志都不会有。
这就是缺陷-7 的修复，落在 `cmd_write()` 循环开头。

### Prompt 4 —— 要不要上多线程并发下载？

```
现在功能已经跑通了（单线程顺序下载）。我有点想把下载改成多线程：
开 4 个线程，每个线程领一个未完成的块，谁先完成谁先置位，理论上 4 倍速度。
请评估一下这个改动的收益和风险，尤其是对「断点续传正确性」的影响。
我们只有一台虚拟机，数据源多半是 localhost 的 HTTP 服务或者本地文件。
```

**AI 回复要点**：给出了 pthread 方案（`pthread_create` + 块队列 + 互斥锁保护位图），
列出需要处理的点：位图并发写、`sio_map_save()` 的原子性在并发下退化、
错误传播、线程退出时机、`-pthread` 链接。
同时也提醒：位图每次提交都要 `fsync` + `rename`，多线程会把这个代价乘以线程数；
如果数据源是本地文件或 localhost，瓶颈根本不在网络。

**我的判断**：**拒绝**。

**理由与落地**（我把它写进了代码注释和 README 的「已知限制」）：

1. **作业没要求**。作业的四条要求是空洞创建、定点写入、断点续传、状态打印，
   并发下载不在评分点上，加了只会引入新的失败面。
2. **会让位图提交时序复杂化**，这是我最不想要的。现在 `sio_map_save()` 是
   「写 `.tmp` → `fsync` → `rename`」，单线程下它是全序的，
   「文件要么是旧的完整版、要么是新的完整版」这句话才成立。
   多线程下两个线程同时 `sio_map_save()` 会互相覆盖 `.tmp` 甚至 `rename` 到一半被抢，
   要么加全局锁（等于把 `fsync` 串行化，收益归零），要么改设计（每线程一份位图分片再合并）——
   后者的复杂度远超这份作业。
3. **收益在这个场景下不成立**。演示用的数据源是 `file://` 或 localhost 的 HTTP，
   瓶颈是 `fsync` 而不是带宽；`fsync` 次数不变，加线程只多消耗调度。
4. 我在 README「已知限制」第 4 条明确写了「单线程顺序下载；未做多连接分块并发（作业未要求，
   且会让位图提交时序复杂化）」，把「不做」当成一个有理由的设计决定交代清楚，
   而不是假装没想到。

### Prompt 5 —— HTTP 数据源：自己实现 socket，还是调 curl？

```
数据源这块我打算自己用 socket 实现 HTTP/1.1 的 Range 请求：连接复用、
自己发 GET + Range: bytes=a-b、自己解析状态行和响应头、自己校验 Content-Range 的起点。
你帮我把这个实现的框架写出来，注意几点：
- 要能识别服务端忽略 Range 返回 200 的情况（这时得在流里跳过前 start 个字节）；
- 长度探测用 Range: bytes=0-0 拿 Content-Range: bytes 0-0/total 里的 total；
- HTTP 响应体必须精确读满 len 字节，短读要当错误处理；
- 超时、重连、EINTR 都要处理。
```

**AI 产出**：约 350 行 socket 实现（`tcp_connect` / `sock_read_full` / `sock_read_line` /
`http_request_range` / `sio_source_probe_size`），逻辑完整，编译通过。

**我的判断**：**部分采纳**——先按 AI 的方案自己实现并使用，实测发现问题后再引入 curl 通道，
**但保留自己实现的 socket 版本作为 curl 不可用时的回退**。

**理由与落地**（分两段）：

**第一段：先用自己实现的。** 理由是自己实现能完全掌控
「`Content-Range` 起点必须等于我请求的 start，否则报 `SIO_ERR_RANGE`」这种校验
（`stat` 说得对不代表数据对，服务端返回错段是最阴的 bug）。
这一段落在 `src/sio_http.c` 的 `http_request_range()`，至今仍在用（`use_curl == 0` 分支）。

**第二段：为什么后来又加了 curl 通道。** 自己维护 HTTP 长连接的坑在实测中暴露了：
- 服务端 200 降级时连接里残留未读完的字节，污染下一个块的请求（这就是缺陷-12）；
- 连接保持、超时重连、`Content-Length` 与实际响应体不一致的处理，
  每一处都要我自己写对，而这些是 curl 二十年踩出来的；
- 更要命的是我根本没法保证「我的 HTTP 实现是对的」——作业要考的是文件 IO，不是 HTTP 协议栈。

所以我加了一条 `curl -r a-b` 通道（`curl_pread()` / `curl_probe_size()`），
`-r a-b` 恰好等价于 `Range: bytes=a-b`，`--fail` 让 4xx/5xx 变成非零退出码，
`pclose()` 的返回值参与成功判定——**`pclose != 0` 时即使收到了部分字节也返回 -1**，
不允许把半段响应当成功。但**没有删掉 socket 实现**：
`have_curl()` 用 `system("command -v curl")` 探测，拿不到就告警
「未找到 curl，回退到内置 socket 实现」。两条通道都跑过端到端测试。
这是典型的「部分采纳」：AI 的方案没被扔掉，而是从唯一方案降级为回退方案。

### Prompt 6 —— 用 Python 的 `http.server` 当数据源行不行？

```
演示脚本里我想直接 `python3 -m http.server 8099` 当 HTTP 数据源，
这样不用额外写服务端代码。我的下载器每个块发一次 `Range: bytes=a-b`，
期望拿到 206 Partial Content。这个方案可行吗？如果不行，我需要自己写什么？
```

**AI 回复要点**：`http.server` 的 `SimpleHTTPRequestHandler` 在 Python 3.10 里
**不支持 `Range` 请求头**，任何 GET 都返回 `200` + 整个文件；
AI 建议改用 `RangeHTTPServer` 之类的第三方包，或者干脆接受 200 降级。

**我的判断**：**拒绝**（拒绝「用 `http.server` 当 Range 数据源」这个前提，也拒绝引入第三方包）。

**理由与落地**：我在虚拟机里实测确认了 AI 的说法——
用 `python3 -m http.server` 跑演示时，下载器的 `--verbose` 日志里出现的是
「服务端不支持 Range（返回 200），按整文件流式跳过 N 字节」，
每一块都要把整个 8MiB 文件从头读一遍再丢掉前 N 字节，
不仅慢，还**完全看不出 Range 断点请求的价值**——演示就变成了在证明「我的降级路径能用」，
而不是在证明「我按需取段」。
引入第三方包更不行：作业要求可复现，评阅人机器上不一定装得上。

所以我照着 RFC 7233 自己写了一个最小实现 `tests/range_server.py`（约 100 行）：
用 `ThreadingHTTPServer` + `BaseHTTPRequestHandler`，手工解析 `bytes=(\d*)-(\d*)`，
支持 `bytes=a-b`、`bytes=a-`、`bytes=-N` 三种形式，区间越界返回 `416` + `Content-Range: bytes */size`，
正常返回 `206` + `Content-Range: bytes start-end/size` + `Accept-Ranges: bytes`，
并设置 `protocol_version = "HTTP/1.1"` 以支持长连接。
演示脚本开头会用 `curl -s -D - -H 'Range: bytes=1000-1999'` 先自证服务端确实回 206，
再去跑下载器——**先证明测试环境是对的，再去测被测对象**。
这个习惯后来直接帮我捞出了缺陷-12（HTTP 200 降级路径的连接残留）。

### Prompt 7 —— 块大小 / 头区大小怎么选，非块对齐的尾块怎么算

```
现在要定参数默认值和分块算法，请给建议并说明理由：
1) --block 默认多少合适？上限设多少？块大小和 fsync 次数、内存占用、磁盘占用粒度之间怎么权衡？
2) --head 是什么东西？我为什么需要一个「前缀连续区」？默认给多大？
3) 最关键：总大小不是块大小整数倍时，尾块怎么处理？我的想法是块数用 ceil(total/block)，
   最后一块只写 total - start 个字节。但如果我还有一个 head 区，块数到底怎么算？
   请你把「头区算不算一块」这件事说清楚，并给出 nblocks 的精确公式和一个具体数字例子。
   我担心这里算错会出现「程序说全部完成但文件尾部是空洞」的情况。
```

**AI 回复要点**：

- 块大小默认 64KiB 是常见折中：太小 → `fsync`/HTTP 请求次数暴涨；太大 → 单块失败的重传代价和内存占用上升。上限给 64MiB 防止手滑；
- `head` 区是「前缀连续区」，用来模拟真实下载器前面那段必须连续落盘的数据（元数据/索引），
  默认 4KiB（一个文件系统块），也方便演示「头区 + 若干数据块」的混合记账；
- 非对齐时用 `ceil`，尾块 `len = total - start`；头区**应当算作独立的一块**，
  `nblocks = (head > 0 ? 1 : 0) + ceil((total - head) / block)`。

**我的判断**：**采纳**（参数取值和公式都对），但**我坚持先用一个具体数字把公式验算一遍**。

**理由与落地**：AI 给的公式是对的，而且是**在缺陷-10 已经造成过一次实测数据丢失之后**才纠正过来的
（初版给的是 `ceil((total - head) / block)`，把 head 当成了「第 0 块」）。
这件事让我确立了一条规矩：**边界公式不能只看公式，必须代一个非对齐的具体数字进去算。**

我用的验算例：`total = 128*1024 + 12345 = 143417`，`head = 100`，`block = 64K`：

```
正确：nblocks = 1 + ceil((143417 - 100) / 65536) = 1 + ceil(2.187) = 1 + 3 = 4
      块 0: [0, 100)        长度 100
      块 1: [100, 65636)    长度 65536
      块 2: [65636, 131172) 长度 65536
      块 3: [131172, 143417) 长度 12245   ← 尾块，不满一块
      合计 100 + 65536*2 + 12245 = 143417 ✅

错误（AI 初版）：nblocks = ceil(143317 / 65536) = 3 → 只跑到 131172，尾部 12245 字节永远是空洞
```

这个例子现在是 `tests/test_all.sh` 里 T5.3 的用例数据（128K + 12345 字节的随机源，`--head=100`），
同时也是 `src/sio_bitmap.c` 里 `sio_map_nblocks()` 上方那段注释的内容。

## 4. AI 代码审查与实测发现的缺陷（重点）

审查方式：让 AI 以「找 bug」模式审查初版（Prompt：「不要夸，只列问题，每条按
现象 / 根本原因 / 验证方法 / 修复方案写」），
然后**每一条都在虚拟机上复现一次**——复现不出来的不算缺陷，复现出来的才改。
下面 12 条全部是**实测复现过**的。

### 缺陷-1：`_GNU_SOURCE` 重复定义

- **现象**：`make` 时每个 `.c` 都刷一行 `warning: "_GNU_SOURCE" redefined`。
- **根因**：Makefile 的 `CPPFLAGS` 里传了 `-D_GNU_SOURCE`，
  而每个源文件开头又写了 `#define _GNU_SOURCE`（为了让 `pread`/`pwrite`/`ftruncate` 拿到正确的原型），
  两处同时生效。
- **验证方式**：`make clean && make 2>&1 | grep -c redefined`，改了之后为 0。
- **修复**：Makefile 不再传该宏，统一由源文件自己 `#define`。
  落在 `Makefile` 第 26–28 行的注释与 `CPPFLAGS` 定义。
  **为什么让源文件保留**：宏必须在包含任何系统头之前生效，
  写在源文件第一行最可靠；Makefile 传参一旦有人漏改就全盘失效。
- **附带收获**：这条告警本身无害，但「零告警」是本作业的硬承诺，
  有一条告警就说明我的编译验证不严格——**告警清零以后，后面几条真正的类型问题才浮出水面。**

### 缺陷-2：`sio_parse_size()` 返回 -1 与「-1 = 不限」撞值

- **现象**：`sparseio write --limit=abc ...` 被静默当成「不限」，
  程序一路下到底，退出码 0，看起来完全正常。
- **根因**：`sio_parse_size()` 解析失败返回 `-1`；而 `--limit` 的合法语义里
  `-1` 恰好表示「不限」（`opts_default()` 里 `o->limit = -1`）。
  两者在 `parse_opts()` 里无法区分，`--head=abc` 同理会静默退化成默认 4K。
- **验证方式**：`./sparseio write --target=t --source=file://s --limit=abc; echo $?`
  → 改前输出 0 并下完整个文件；改后输出 2 并打印 `--limit 解析失败`。
- **修复**：在 `parse_opts()` 里为每个数值选项加 `seen_block / seen_head / seen_size /
  seen_limit / seen_delay / seen_retry` 标记，把「没给这个参数（用默认值）」
  和「给了但解析失败（报错退出）」彻底分开。
  落在 `src/sio_main.c` 的 `parse_opts()`（第 111–166 行）。

### 缺陷-3：`--block=0` 未被拒绝，程序「成功」下了 0 字节

- **现象**：`--block=0` 时程序打印「全部块提交完成：0 块，本次新写入 0 字节」，退出码 0。
- **根因**：`sio_map_nblocks()` 里有 `if (block_size == 0) return 0;` 的保护，
  于是 `nblocks = 0`，`cmd_write()` 的 for 循环一次都不进，
  直接落到「全部块提交完成」的日志和 `rc = SIO_OK`。
  **保护性返回 0 反而把一个参数错误伪装成了一次成功运行。**
- **验证方式**：`./sparseio create --target=t --size=1M --block=0` 再 `write`，
  观察 `status` 里 `blocks_total = 0`、目标文件全空洞。
- **修复**：在 `parse_opts()` 里显式拒绝非正数块大小
  （`if (seen_block && o->block <= 0) return SIO_ERR_USAGE;`），
  并保留 `sio_map_nblocks()` 里的 0 保护作为最后一道防线。
  教训：**「返回 0 表示没什么可做」的写法，在参数校验缺失时就是静默错误。**

### 缺陷-4：死代码 `resolve_total()` 与未使用变量

- **现象**：编译报 `-Wunused-function`（`resolve_total` 定义了但没人调用）
  和 `-Wunused-variable`（`cmd_verify` 里的 `done`）。
- **根因**：`resolve_total()` 是初版用来算「目标大小取 `--size` 还是源大小」的辅助函数，
  后来这个判断被 AI 内联进了 `cmd_create()`（`if (o->size > 0) ... else if (src_size > 0) ...`），
  函数本体忘了删；`cmd_verify` 里的 `done` 也是重构时留下的残骸。
- **验证方式**：`make clean && make 2>&1 | grep -E 'unused'`，改后为空。
- **修复**：直接删掉 `resolve_total()` 和 `done`。
  **为什么不是「加 `(void)done;` 糊过去」**：死代码会误导后来读代码的人
  （包括我自己），以为还有另一条计算路径存在；而且两份同样的逻辑必然会在某次修改后分叉。

### 缺陷-5：`cmd_create` 把 `src_size` 硬编码为 0，位图永远记「源长度未知」

- **现象**：`create --source=file:///tmp/src.bin` 之后，
  `write` 阶段无法提前发现「目标 > 源」，只能等某个块真的读不到才报错，
  甚至可能把整段尾部留成空洞后「成功」退出。位图头部 `src_size` 一直是 0。
- **根因**：`cmd_create()` 调用 `sio_map_open()` 时把 `src_size` 位置写成了字面量 `0`，
  而 `main()` 明明已经探测到源长度并通过参数传了进来（`src_size` 形参没人用）。
- **验证方式**：`create --source=<1MiB 文件> --size=2M`，
  用 `--verbose` 观察 `write` 阶段是否直接报「目标大小超过源大小」（退出码 4）。
- **修复**：把探测到的 `src_size` 如实写进位图头部，`write` 阶段续传时从位图就能拿到源长度。
  落在 `src/sio_main.c` 的 `cmd_create()`（`sio_map_open(..., src_size, o->source)`）。
  这条的价值在于：**它是「参数在函数签名里存在但实际被忽略」的典型**，
  光看代码结构看不出来，只有把 `create` 到 `write` 的完整链路走一遍才会暴露。

### 缺陷-6：`len == 0` 时 `end` 下溢，拼出非法的 `Range` 请求头

- **现象**：在块长度为 0 的边界（`total == head` 且只剩头区块、
  或调用方传入零长度请求）会出现请求头
  `Range: bytes=X-18446744073709551615`，服务端返回 416，下载器报区间错误。
- **根因**：`http_request_range()` 里 `uint64_t end = off + len - 1;`，
  `len == 0` 时 `off + 0 - 1` 在无符号运算下回绕成 `UINT64_MAX`。
- **验证方式**：加临时调试打印或在 `--head` 等于 `--size` 的构造下抓请求头，
  看到 `end` 是 `18446744073709551615`。
- **修复**：`uint64_t end = (len == 0) ? off : (off + (uint64_t)len - 1);`
  落在 `src/sio_http.c` 的 `http_request_range()`。
  **这类 bug 的通用特征**：`a + b - 1` 形式的长度计算，`b` 一旦可能为 0 就必须单独兜底。

### 缺陷-7：Ctrl-C 之后还要等 retry 次才退出

- **现象**：`--delay=300` 跑着按 Ctrl-C，程序不立刻退出，
  日志里先刷出两三条「块 N 读取失败（第 1/2 次，期望 262144 实际 -1）」，
  等重试次数耗尽才停下来。
- **根因**：信号处理故意不加 `SA_RESTART`（Prompt 3），
  所以阻塞中的 `pread`/`recv` 会带着 `EINTR` 提前返回；
  `cmd_write()` 的重试循环只看返回值不等于 `len` 就判「读取失败」并重试，
  白白把 `--retry` 次用完。**这是「正确的设计」和「粗糙的错误处理」打架。**
- **验证方式**：`--delay=300 --retry=3` 跑起来按 Ctrl-C，
  数一数退出前有几行「读取失败」；改后为 0 行，且退出码仍是 130。
- **修复**：在**每块开始前**检查 `sio_interrupted()`，一旦置位就在块边界干净退出：
  「收到 SIGINT，停止写入（进度已保存到位图）」。
  落在 `src/sio_main.c` 的 `cmd_write()` 循环开头。
  我没有采纳 AI 的「在重试循环里判断」版本，因为那会留下误导性的失败日志，
  演示时看起来像程序出错了。

### 缺陷-8：位图参数不一致时 `status` 误报「该文件未由本工具 create」

- **现象**：目标文件明明是本工具创建的，只因当前命令的 `--block`/`--head`/`--size`
  与位图记录不符，`status` 就打印「进度位图：无（该文件未由本工具 create）」，
  用户会去怀疑文件本身，而不是去怀疑自己的参数。
- **根因**：`cmd_status()` 里 `sio_map_open()` 的所有失败（不存在 / 损坏 / 参数不一致）
  都返回 `SIO_ERR_BITMAP`，而打印分支只区分了「成功」和「失败」两种情况。
- **验证方式**：`create --block=256K` 建好、`status --block=128K`，
  改前输出「该文件未由本工具 create」，改后输出正确指引。
- **修复**：区分 `SIO_ERR_BITMAP`，打印
  「进度位图：<path>（存在但与当前 --block/--head/--size 不一致，请改回 create 时的参数）」。
  落在 `src/sio_main.c` 的 `cmd_status()` 末段（`else if (map_rc == SIO_ERR_BITMAP)` 分支）。

### 缺陷-9：`sio_map_save()` 在 `rename` 后没有 `fsync` 父目录

- **现象**：正常运行看不出来；只有在「写完位图 → `rename` 成功 → 立刻掉电」
  这个窗口里才会体现为位图回退到旧版本（表现为「进度倒退若干块」）。
- **根因**：`rename()` 保证的是**原子替换**，不保证**已经持久化**。
  新目录项落在目录的 dentry 里，如果目录本身没 `fsync`，
  掉电后可能只看到旧名字或旧 inode——这与我在 Prompt 2 里承诺的
  「位图要么是旧的完整版，要么是新的完整版」不符（因为「新完整版」可能丢）。
- **验证方式**：`strace -e trace=fsync,rename,openat ./sparseio write ...`
  观察 `rename` 之后是否还有一次对父目录的 `fsync`；改前没有，改后有。
- **修复**：`rename` 之后打开父目录并 `fsync(dfd)`，
  **失败只告警不报错**（`sio_log_warn("位图目录 fsync 失败（不影响续传）")`）——
  某些文件系统不支持目录 `fsync`，不应该因此让整个续传失败。
  落在 `src/sio_bitmap.c` 的 `sio_map_save()` 末段。

### 缺陷-10（最严重，实测复现的数据完整性缺陷）：少算一个数据块，尾部字节永久丢失

- **现象**：程序报告「全部块提交完成」、退出码 **0**，
  但目标文件的尾部若干字节**永远是空洞**（全 `0x00`），
  `sha256` 与源不一致，而日志从头到尾没有任何错误。
  实测数据：`total = 143417`、`head = 100`、`block = 64K` 时，
  程序只写了 **131172** 字节，**尾部 12245 字节丢失**。
- **根因**：`sio_map_nblocks()` 初版是
  `return (body + block_size - 1) / block_size;`，
  把 `head` 区**当成了「第 0 块」**，于是数据块数量比实际需要少 1。
  而 `sio_map_block_range()` 计算第 `i` 块的起点是按
  `head + (i - (head>0?1:0)) * block_size` 递推的，
  块数少 1 意味着**最后那一段不足一块的数据永远落不到任何块上**：

  ```
  nblocks = ceil(143317 / 65536) = 3            ← 少了 1
  块 0: [0, 100)         头区
  块 1: [100, 65636)
  块 2: [65636, 131172)                         ← 到此为止
  [131172, 143417) 这 12245 字节不属于任何块 → 永远是空洞
  ```

  注意它**不报错**：循环正常跑完 `i < nblocks`，每个块都成功提交，
  于是打印「全部块提交完成」并返回 `SIO_OK`。
- **验证方式**：这就是 T5.3 用例（`head -c $((128*1024+12345)) /dev/urandom` 造源，
  `--block=64K --head=100`）。改前：
  `sha256sum` 与源不一致、`cmp` 在偏移 131172 处报差异、
  `python3` 逐字节统计显示尾部 12245 字节全为 0。改后：`sha256` 完全一致。
  **三重验证**（sha256 + cmp 偏移 + 逐字节零统计）都指向同一个数字 12245，
  这才确认不是统计口径问题。
- **修复**：把「头区块」显式加回去：
  `return (head_size > 0 ? 1 : 0) + (body + block_size - 1) / block_size;`
  落在 `src/sio_bitmap.c` 的 `sio_map_nblocks()`，
  函数上方保留了这段实测数据作为回归说明。
- **为什么说它最严重**：其他 11 条缺陷要么会报错、要么只影响体验或性能；
  只有这一条会**在日志全绿、退出码 0 的情况下产出错误文件**。
  如果我没写 T5.3 这个非对齐用例，这个 bug 会安安静静地跟着作业一起交上去。
- **教训**：**「全部完成 + 退出码 0」不等于「文件正确」，只有 `sha256` 对比才算数。**
  我把这条写成了硬规则：任何一次演示，最后一步必须是
  `sha256sum 源 目标` 的对比，绝不用「程序说完成了」当结论。

### 缺陷-11：中断分支吞掉了「本次新写入 / 跳过」汇总

- **现象**：Ctrl-C 或 `--limit` 中断时，最后一行输出只剩
  「退出码 130（中断，可重新执行 write 续传）」，
  看不到「本次新写入多少字节、跳过了多少个已完成块」——
  而这两行恰恰是**演示断点续传时最关键的证据**。
- **根因**：汇总日志写在 `cmd_write()` 的正常结束路径上，
  而所有中断分支都是 `goto out`，直接跳到出口，把汇总跳过去了。
- **验证方式**：`write --limit=5` 看最后三行；改前没有汇总，改后有。
- **修复**：把汇总统一挪到出口标签之前打印一次，
  并加 `if (rc == SIO_ERR_INTERRUPT)` 判定避免与正常路径重复输出
  （「中断汇总：本次新写入 N 字节，本次跳过（已完成）M 块，进度已保存到位图」）。
  落在 `src/sio_main.c` 的 `cmd_write()` 的 `out:` 段。
  **顺带解决了一个测试问题**：T3 就是靠解析这行日志里的「本次跳过（已完成）N」
  来断言「续传真的复用了位图」，缺陷-11 修好之前这个断言根本没法写。

### 缺陷-12：HTTP 200 降级路径的连接残留污染下一个块

- **现象**：对着一个不支持 `Range` 的服务端跑 `write`，
  第一块能成功（走 200 降级跳过前 start 字节），
  从第二块起日志里刷出 `ERROR 无法解析状态行: <乱码>`，
  然后疯狂重连，几乎每个块都要重连一次才能勉强前进。
- **根因**：服务端返回 200 时发的是**整个文件**，
  客户端「跳过前 `start` 字节」只是**自己不再读**那一段，
  服务端仍然会把剩余部分写进同一个 socket。
  于是连接里残留着上一次响应没读完的字节，
  下一个块的请求发出去后，读到的「状态行」其实是上一次响应的残留数据。
- **验证方式**：用 `python3 -m http.server`（Python 3.10 不支持 Range，
  必然走 200 分支）跑 `write --verbose`，
  看到「服务端不支持 Range（返回 200），按整文件流式跳过」紧接着就是状态行解析失败；
  用 `strace -e trace=recvfrom,sendto` 能看到连接被反复 `close` + `connect`。
- **修复**：给连接打 `sock_dirty` 标记——走 200 降级路径时置位，
  **读完本块的响应体之后**才关闭连接（不能立刻关，因为调用方马上还要从这个 socket 读数据），
  让下一个块重新建连。206 分支由 `Content-Length` 精确分隔，长连接仍可安全复用。
  落在 `src/sio_http.c` 的 `http_request_range()`（置位）与
  `sio_source_pread()`（读完后关闭）。
- **附带结论**：这也是我后来引入 `curl` 通道的直接原因之一——
  长连接的状态机不好维护，而 curl 已经把这些情况处理了（见 Prompt 5）。

## 5. 测试脚本自身的缺陷（S1–S7）：AI 给的东西不能照抄

AI 写的 `tests/test_all.sh` 第一版跑起来「一片红」，但**报错的都不是被测程序**。
我逐条排查，发现是测试脚本自己的问题。这部分我单独列出来，
因为它最能说明「AI 生成的测试代码必须当作被测对象来审」。

| 编号 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| **S1** | T2、T3、T4 连锁失败，第一处报错是 `write` 退出码 4 | 脚本里 `TOTAL = 6MiB`，但源文件只造了 4MiB。下载器**正确地**拒绝了「目标 > 源」（退出码 4，这就是 T5.4 要验的行为），后续用例全部建在这个失败之上 | 把 `TOTAL` 改成与 `SRC_SIZE` 一致（4MiB），并在脚本里加注释说明「这是测试设计缺陷，不是被测程序缺陷」 |
| **S2** | T5.1 建 128KB 文件时 `create` 退出码 2 | 源只有 128KB，脚本却传 `--block=1M`。`cmd_create()` 里 `if ((uint64_t)o->block > total)` 会**正确地**拒绝块大小大于总大小 | 改成 `--block=64K --head=0` |
| **S3** | T2 断言 `blocks_done == 6` 失败，实际是 7 | 期望值算错：`--limit=7` 计的是**块数**，而「头区」本身算第 0 块，所以是「头区 + 6 个数据块 = 7 块」，不是 6 个数据块 | 断言改成 7，并把「头区算一块」写进注释；同时把 `cmp -n $((4096 + 6*BLOCK))` 的对照区间也按这个口径写 |
| **S4** | T6 段整段没跑，`make` 直接报 `wait: 没有子进程` 并中断 | `wait $WPID 2>/dev/null; rc=$?` 这种写法在 `wait` 失败时返回非 0，在 `make` 调用链里会被当成命令失败；而且 `2>/dev/null` 把解释原因的报错也吞了 | 改成 `rc=0; if wait "$WPID"; then rc=0; else rc=$?; fi`，显式捕获退出码，不让 `wait` 的失败状态外溢 |
| **S5** | T3 里 `SKIPPED` 和 `NEWBYTES` 解析出来都是 0（空值） | 断言写成 `RESUME_OUT=$($BIN write ...)`，**没加 `2>&1`**；而程序的全部日志都走 stderr（`sio_util.c` 的 `vlog()` 用 `fprintf(stderr, ...)`），于是 `RESUME_OUT` 是空字符串，`grep` 自然什么都取不到，最后被 `${SKIPPED:-0}` 兜成 0，误判成「一个块都没跳过」 | 所有需要解析日志的地方统一加 `2>&1`，并在注释里写明「日志走 stderr」这个约定 |
| **S6** | T3 的「跳过已完成块」断言测不出东西 | 脚本先跑完整的续传把文件下完（17/17），**再**去做「跳过已完成块」的断言——那时所有块都已完成，只能得到「跳过 17 块」，完全测不到「复用断点、只补剩余」的语义 | 改成先跑 `--limit=1`（只补 1 块），此时文件处于「未完成」状态，才能观察到「跳过 7 块 + 新写入 1 块 = 256K」 |
| **S7** | T6 的 SIGINT 用例偶尔拿到退出码 0 | 脚本用 `--delay=60`，17 个块在 1.5s 内就跑完了，`kill -INT` 打到的是一个**已经正常退出**的进程上（那时 `$WPID` 可能已被复用或已是僵尸），退出码自然是 0 | 改成 `--delay=300`（17 块 × 300ms ≈ 5.1s ≫ 1.5s），保证信号发出时进程一定还在下载中 |

**从这 7 条里我总结出的三条规矩，后来都用到了项目上**：

1. **测试脚本也是代码，也要审查。** AI 能写出逻辑通顺的断言，但对「这个数字具体是多少」
   （S3 的 6 vs 7）、「这个进程还在不在」（S7）、「日志到底流向哪个 fd」（S5）这类
   **必须与实现细节对齐**的地方，它会靠猜。
2. **红色不一定说明被测程序坏了。** S1、S2 的报错其实是下载器**正确地**拒绝了错误输入，
   说明被测对象的参数校验是好的；如果不加分辨就去「修程序」，会把正确的行为改坏。
3. **先证明环境，再证明程序。** 每次演示前先用 `curl -D -` 确认服务端真的回 206
   （`demo.sh` 第 46–48 行），先用 `strace` 确认 `fsync` 顺序
   （缺陷-9 的验证方式）——**先把「我以为的测试环境」证实，再去看程序的输出。**

## 7. 最终结论

### 7.1 AI 真正加速的部分

- **技术路线一次定对**：`ftruncate` 造空洞 + `pwrite` 定点写 + 位图记账，
  省掉了我翻 `man 2 open/ftruncate/pwrite/stat` 反复试错的时间；
- **测试用例设计命中了真实缺陷**：「目标 > 源」「完成后重跑」「非块对齐」三条里，
  非块对齐那条直接捞出了最严重的缺陷-10；
- **文档的结构意识**：功能对照表 + 「已知限制」的写法，
  逼着我把「哪些数字是估计值」「哪些场景没测」交代清楚；
- **代码审查的广度**：12 条缺陷里 7 条是它自己找出来的，
  尤其是缺陷-10 的根因分析（把 head 当成第 0 块）写得很准。

### 7.2 必须人工把关的部分

| 把关点 | 具体的坑 |
| --- | --- |
| **正确性顺序** | 「先置位还是先 `fsync`」这类顺序问题，AI 会给出**看起来合理但方向相反**的答案，而且语气很自信 |
| **整数与边界** | `a + b - 1` 下溢、`nblocks` 少算一块、`-1` 撞值——C 语言三大经典坑，AI 初版全部踩了 |
| **「静默成功」的错误** | 缺陷-3（0 字节却报完成）、缺陷-10（尾部丢失却退出码 0）都属于日志全绿但结果是错的，这类 bug 只能靠**独立的验证手段**（`sha256`、逐字节统计）抓出来，不能靠读日志 |
| **测试脚本的可用性** | S1–S7 说明 AI 写的测试代码必须自己跑一遍并逐条排错 |
| **文档诚实度** | 「多线程」「HTTPS」「精确统计」三处凭空写的功能，不核对代码就会直接交上去 |

### 7.3 我给自己立的四条规矩

1. **任何结论必须落到命令和数字上。** 「`--head=100` 时尾部丢 12245 字节」比
   「非对齐情况可能有问题」有用一百倍，而且能被复现、被回归测试锁住。
2. **先证明环境，再证明程序。** 服务端先 `curl` 验 206，`fsync` 顺序先 `strace` 看，
   运行环境（`uname` / `df -T` / `cc --version`）先打印进测试日志。
3. **「程序说完成了」不算数，`sha256` 一致才算数。** 这是缺陷-10 用 12245 个丢失字节换来的。
4. **AI 的产出默认是「待验证的草稿」。** 采纳与否不看它说得多有道理，
   只看我能不能在虚拟机上把这个说法复现出来。

> 一句话总结：**AI 负责把路铺快，人负责决定走哪条路、以及在哪个路口停车检查。**
> 这一版代码里，凡是「AI 说对了我采纳」的地方都省了时间；
> 凡是「AI 说错了我拦住」的地方，保住的是这份作业的数据正确性。
