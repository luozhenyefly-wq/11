## 1. 测试策略

### 1.1 第一步不是写用例，是把作业要求翻译成「可判定命题」

作业给的是四句自然语言（create / write / 续传 / status），自然语言没法断言。我先做了一次翻译：
**每条要求 → 一个能返回真/假的命题 → 一个不依赖被测程序的判定手段**。
关键是最后一句：判定手段不能来自被测程序自己的输出，否则就是「自己证明自己」。

| 作业要求原文 | 我翻译的可判定命题 | 判定手段（独立于被测程序） | 落地用例 |
| --- | --- | --- | --- |
| create 生成空洞文件，逻辑大小 ≥128KB | `st_size == 指定的 4MiB`；`st_size < 131072` 的命令必须非 0 退出 | shell `stat -c %s` / 退出码 | T1、T5.2 |
| 未写入区不占磁盘块 | 建完文件后 `st_blocks*512 < 64KiB`（新建时应为 0） | shell `stat -c %b` × 512 | T1 |
| write 定点写入，不破坏其余空洞 | 已写区间的**前 N 字节**与源逐字节相同；未写区间的非零字节数 == 0；磁盘占用只随已写块增长 | GNU `cmp -n`；Python 逐字节统计非零；`stat -c %b` 上界 | T2 |
| 断点续传（Ctrl-C 后不重下） | 中断后重跑，`blocks_done` 保持不变、本次新写入字节 == 剩余块字节、退出码 0 | `--json` 输出 + 日志正则 + `sha256sum` 交叉验证 | T3、T6 |
| status 打印逻辑大小 / 实际占块数 / 空洞占比 | 输出的 `logical_size` 与 `stat` 一致；`blocks_done/blocks_total` 与断言中的期望块数一致 | `status --json` 的字段值 | T2、T3、T4、T6 |
| 数据正确（隐含的底线） | 目标文件 `sha256` == 源 `sha256`；`verify` 逐块通过 | `sha256sum`（外部实现，不是我自己写的 SHA-256） | T4、T5.1、T5.3、T6 |

两个翻译时的自觉约束：

1. **退出码当契约用。** 程序定义了 `SIO_OK=0 / USAGE=2 / IO=3 / RANGE=4 / BITMAP=5 / NET=6 / VERIFY=7 / INTERRUPT=130`，
   这些就是脚本能抓到的最稳定的接口。凡是「应该被拒绝」的场景，我一律断言**具体**退出码，
   而不是「非 0 就行」——`2` 和 `5` 混起来就分不清是「参数写错」还是「位图对不上」。
2. **期望值必须在脚本里独立算出来。** 例如 T2 里 `cmp -n` 的字节数是我在脚本里按
   `4096 + 6*BLOCK` 算的，不是从程序日志里抠出来的；块数 17 也是我按
   `1 + ceil((4194304-4096)/262144)` 手算后写进注释的。**用程序的输出当期望值，等于没测。**

### 1.2 无网络自动化：用 `file://` 源跑功能用例

`tests/test_all.sh` 里除了 T5.4 之外的**全部**用例都用 `--source=file://$SRC`。
这么选不是图省事，而是有明确理由：

- **可复现**：源就是本地一个 4MiB 文件，`sha256` 固定，不依赖 DNS、端口、代理、对端限速；
  在虚拟机的离线快照上照样跑出同样的结果。测试数据在脚本开头用 `head -c ... /dev/urandom` 现造，
  所以每次运行的源内容不同、但**断言结构完全相同**（这一点很重要：随机数据能抓到「把块偏移算错但碰巧对齐」的错）。
- **覆盖率不降级**：看 `src/sio_http.c` 的实现，`file://` 源走 `open()` + `pread()`，
  HTTP 源走 `Range` 请求，但**两者都被封装在同一个 `sio_source_pread(src, buf, len, off)` 接口后面**
  （`sio_common.h` 里是不透明类型 `sio_source`）。而断点续传的全部复杂度——块范围计算
  （`sio_map_block_range`）、位图记账（`sio_map_set/save`）、中断与恢复——都在这个接口的**上层**。
  换句话说：只要 T1–T3、T6 用 `file://` 把「块语义」测死，HTTP 只是把 `pread` 换了个实现，
  不需要在每个边界用例里再叠一层网络不确定性。
- **不需要额外进程**：没有起服务、没有端口占用、没有「上一个测试的服务端还活着」这类
  串扰问题（`tests/demo.sh` 里专门用 `setsid` + 杀进程组来防这个坑，恰恰说明这类问题真实存在）。

### 1.3 真实 HTTP Range 端到端：自写 `tests/range_server.py`

只用 `file://` 测有一个致命盲区：**它证明不了程序真的在发 Range 请求、真的在处理 206。**
如果 `sio_http.c` 把 `Range` 头拼错、或者把 `Content-Range` 起点的校验写反，
`file://` 用例全绿也发现不了。所以我写了一个最小的静态服务器 `tests/range_server.py`（约 100 行）：

- 解析 `Range: bytes=a-b` / `bytes=-N`，命中就回 **206 Partial Content** + `Content-Range: bytes a-b/size`；
- 回 `Accept-Ranges: bytes`，并且**只发送被请求的那一段**（`f.seek(start)` 后按 64KiB 分片写）；
- 起点越界或 `start > end` 时回 **416**（正好对上下载器里 `status == 416 → SIO_ERR_RANGE` 的分支）；
- 用 `ThreadingHTTPServer` + `HTTP/1.1`，因此长连接和并发连接都能测。

为什么不用 Python 自带的 `python3 -m http.server`：它忽略 `Range` 头，任何 GET 都回 `200` + 整个文件，
下载器只能退化到「整文件流式跳过」（`sio_http.c` 里的 200 降级分支），
**看起来也下载成功、sha256 也对**，但整个 Range 路径一行都没被执行到——这正是最容易被自欺的测试。
（生态里 `RangeHTTPServer`、`rasterio/tests/rangehttpserver.py` 之类脚本大量存在，也是同一个原因。
参考：[danvk/RangeHTTPServer](https://github.com/danvk/RangeHTTPServer)、[rasterio rangehttpserver.py](https://github.com/rasterio/rasterio/blob/86f64d952344fde161e49708d3c6c5787169953b/tests/rangehttpserver.py)。）

端到端测试我坚持**分两层取证**，而不是「跑完 sha256 对上了就算过」：

```bash
# 第一层：先证明服务端真的回 206（这一步不涉及被测程序，是环境自检）
curl -s -D - -o /dev/null -H 'Range: bytes=1000-1999' \
     http://127.0.0.1:8099/server_file.bin
#   期望看到: HTTP/1.1 206 Partial Content / Content-Range: bytes 1000-1999/8388608

# 第二层：再让下载器以 256K 块去下，观察每块一次 Range 请求与「已完成偏移 [off, +len)」
sparseio create --target=dl.bin --source=http://127.0.0.1:8099/server_file.bin --block=256K --head=64K
sparseio write  --target=dl.bin --source=http://127.0.0.1:8099/server_file.bin --block=256K --head=64K --limit=5
sparseio write  --target=dl.bin --source=http://127.0.0.1:8099/server_file.bin --block=256K --head=64K   # 续传
sparseio verify --target=dl.bin --source=http://127.0.0.1:8099/server_file.bin --block=256K --head=64K
```

这一层就是 `bash tests/demo.sh` 干的事（8MiB 源、256K 块、头区 64K、先下 5 块再续传）。
**先自检服务端、再测客户端**的顺序很重要：如果 206 断言不过，那失败的是我的测试环境，
而不是下载器——这样报错时不会指错方向。

### 1.4 三档「取证强度」

我把断言分成三档，避免出现「所有用例都只测了退出码」这种虚假覆盖：

| 档位 | 判据 | 例子 | 能抓到什么 |
| --- | --- | --- | --- |
| 弱（行为存在性） | 退出码 / 文件存在 | `create` 退出码 0；`.sio` 位图文件已生成 | 崩没崩、走没走到 |
| 中（数值契约） | `stat`、`--json` 字段、日志里的计数 | 逻辑大小 4194304；`blocks_done == 7`；跳过 7 块 | 算错了块数、记账漏了 |
| 强（内容比对） | `sha256sum`、`cmp`、Python 逐字节扫 | 目标 sha256 == 源 sha256；未写区间非零字节 == 0 | **静默数据损坏**——程序说成功但数据是错的 |

强档是核心。这个作业里最有价值的缺陷（见第 5 节）全部是「程序报告成功、退出码 0，但数据不对」，
只有强档断言能抓到。所以我在 T1–T6 每一组里都至少放了一条强档断言。

## 2. AI 辅助生成测试用例的过程

我把 AI 当「会自信地写出跑得通但测不到东西的用例」的搭档：**它出方向，我定断言、我做取舍、我负责实测。**

### Prompt 1（把要求拆成可判定命题，先别写用例）

```
作业要求是四条：create 出逻辑 >=128KB 的空洞文件、write 用 lseek/write 定点写入不破坏其余空洞、
Ctrl-C 后能断点续传、status 打印逻辑大小/实际占块数/空洞占比。
我要写一个 bash 测试脚本，要求能在 Ubuntu 22.04 上无人值守跑完。
先不要写用例，先帮我把每条要求翻译成"可判定命题"，并说明每个命题用什么命令判定：
哪些能用 stat/sha256sum/cmp 判定，哪些必须自己扫字节，哪些只能靠退出码。
同时告诉我：有哪些要求其实无法用自动断言证明，只能靠人工看输出——这类我宁可写进"局限"里，
也不要写一条假装测了的用例。
```

**AI 给的方向**：要求我区分「结构属性」（`st_size`/`st_blocks`）与「内容属性」（sha256/逐字节）；
提醒「≥128KB 是**下限**不是定值」，所以拒绝用例应该是 `--size=65536` 必须失败，而不是断言必须等于 128KB；
并指出「空洞没被破坏」这件事**无法用 sha256 证明**（因为 sha256 只对整文件比对，源里本来就有 0x00 字节），
必须靠「未写区间的非零字节计数 == 0」这种定向扫描。

**我的取舍**：全部采纳。第 3 条尤其关键——它让我意识到「目标 sha256 == 源 sha256」这条强断言
**不能**替代「空洞未被破坏」，两者必须都有。这也是 T2 里那段 Python 逐字节扫描存在的原因。

### Prompt 2（让 AI 找「看着成功其实错了」的用例）

```
这是下载器的实现（附 sio_main.c / sio_bitmap.c）。
请设计测试用例，要求：
1. 覆盖作业四条功能要求；
2. 重点想「什么输入会让它悄悄出错但看日志又是成功的」——这类用例最有价值；
3. 每个用例给出：前置条件、命令、期望退出码、期望断言、如果失败说明哪里坏了。
```

**AI 给的方向（我原来没想到的）**：

| AI 提出的用例 | 为什么有价值 | 我的决定 |
| --- | --- | --- |
| 目标大小 > 源大小 | 会撑出一段永远填不上的尾部，程序若不拒绝就会「成功」退出 | **采纳** → T5.4（要求 exit 4） |
| 完成后再次 `write` | 幂等性：应「新写入 0 字节」而不是重下 | **采纳** → T5.5 |
| 非块对齐的大小（128K+12345） | 尾块不满，`sio_map_block_range` 的边界最容易算错 | **采纳** → T5.3，**并真的抓到了缺陷**（第 5.1 节） |
| 用真 `SIGINT` 而不是 `--limit` | `--limit` 是程序主动退出，走的是同一条码路；真信号会打断阻塞系统调用，是完全不同的路径 | **采纳** → T6（`setsid` + `kill -INT`） |
| 反复 `kill -9` + 重启，验证位图原子性 | 方向对，但只能「撞」写位图的微秒级窗口 | **放弃**，改为代码论证 + 写进局限（第 7 节第 4 条） |

**AI 提错被我否掉的一条**：AI 建议用 `timeout 2 ./sparseio write ...` 来模拟中断。
我拒绝了——`timeout` 发的信号与 Ctrl-C 路径不同，而且它还会带 `SIGKILL` 兜底，
断言就变成「在测 `timeout` 而不是在测我的信号处理」，退出码也不再是 130。
改成 `setsid` + 显式 `kill -INT` 到整个进程组。

### Prompt 3（怎么证明「真的跳过了」而不是「从头重下碰巧也对」）

```
现在只测断点续传。我的担心是：脚本很容易写成"跑完了 write、退出码 0，就算续传成功"——
但这样根本证明不了它复用了断点，也可能只是从头重下了一遍，结果碰巧一样。
请给我一组用例，要能区分这三种情况：
(a) 真的跳过已完成块、只补剩余块；(b) 从头重下、结果碰巧正确；(c) 跳过了但仍报告成功。
每条用例写清楚：怎么构造前置状态、从哪一行输出或哪个数字读出"跳过了几块"、
以及如果被测程序把日志写到 stderr，脚本该怎么取到那行日志。
```

**AI 给的方向**：不要让文件先跑完再断言（那时只能观察到「跳过 17/17」，
无法区分「复用断点」和「碰巧全跳过」）；应该让文件保持**未完成**状态，
再验证「跳过数 == 中断时已完成数」且「本次新写入字节 == 恰好补上的块字节数」；
取日志必须 `2>&1`。

**我的取舍**：采纳，落地为 T3 的两条断言——
`--limit=1` 时「本次跳过（已完成）7」+「本次新写入 262144」。这两条一起才能构成
「复用断点、只补一块」的正证据。这条建议还顺带修掉了我原脚本的一个真缺陷
（原脚本先跑完整续传再断言，只能得到「跳过 17 块」，**测不到断点语义**，见 5.3 节缺陷-S6）。

### Prompt 4（HTTP 端到端怎么做才算真的测到了）

```
我的下载器有两个数据源：file:// 本地文件和 http:// 的 Range 请求。
策略上我想分层：绝大多数功能用例用 file:// 跑（不依赖网络、结果可复现），
另外单独做一组 HTTP 端到端用例证明它真的在发 Range: bytes=a-b 并处理 206。
请告诉我：
1) 只用 file:// 测，有哪些东西是测不到的（列出来）；
2) 用 Python 起本地 HTTP 服务做端到端，要注意哪些"测试自己会骗人"的坑；
3) 怎么在不改被测代码的前提下，让脚本能证明"服务端返回的是 206 而不是 200"。
```

**AI 给的方向**：`file://` 测不到「请求头拼装、`Content-Range` 起点校验、206/200/416 分支、长连接复用」；
`python3 -m http.server` 忽略 `Range` 会回 200，用它做源会**静默走降级路径**，
必须自己写一个回 206 的服务器；证明 206 要用 `curl -D -` 直接看响应头（这一步完全不经过被测程序）。

**我的取舍**：采纳，落地为 `tests/range_server.py` + `tests/demo.sh` 的两层取证结构（见 1.3 节）。
AI 还建议「起真实公网 URL 当源」，我**放弃**了：外网下载慢、会变、离线就挂，
测出来的失败还分不清是网络问题还是代码问题——与「可复现」直接冲突。

### 2.5 取舍汇总

| # | AI 的建议 | 我的决定 | 理由 |
| --- | --- | --- | --- |
| 1 | 目标 > 源、完成后重跑、非块对齐、真 SIGINT | **采纳** | 四条全部命中真实风险，其中非块对齐抓到实际缺陷 |
| 2 | `timeout 2` 模拟中断 | **拒绝** | 信号路径不同且带 `SIGKILL` 兜底，断言会测错对象 |
| 3 | 用公网 URL 做端到端源 | **拒绝** | 不可复现、离线即挂，失败原因不可归因 |
| 4 | 反复 `kill -9` 撞位图写入窗口 | **放弃** | 概率性用例，跑十次可能九次撞不上，脚本会变「薛定谔的测试」 |
| 5 | 用 `LD_PRELOAD` 注入 `pwrite`/`read` 失败来测 `--retry` | **放弃（环境限制）** | 客户机上为一次重试路径编译 hook 库，成本高于收益；改为用真实中断（T2/T6）覆盖「失败后保留断点」的语义 |
| 6 | 多进程并发写同一目标 | **放弃** | 作业未要求，且位图无跨进程锁，测出来的是「不支持」而非「错」，会污染用例集 |
| 7 | 断言 `st_blocks*512` 的精确值 | **拒绝，改成上界** | ext4 分配粒度 4KiB + extent 预分配，精确值不稳定；改成 `< 64KiB`、`< 已写数据 + 8 块` |
| 8 | 用 `cmp` 与 `/dev/zero` 比对未写区间 | **部分采纳** | 「一致/不一致」的诊断信息太弱；改成 Python 统计**非零字节个数**，能直接看出污染规模 |
| 9 | 参数一致性保护（改 `--block` 必须拒绝） | **我自己补的**（AI 没提） | 「换了分块策略静默重下」会把已写数据覆盖成错位内容，属于静默损坏，落地为 T5.6 |
| 10 | 在 `tmpfs`/`btrfs` 上复测稀疏语义 | **放弃（环境限制）** | 客户机只有 ext4 根分区，无额外可格式化块设备；写进局限 |

## 3. 用例清单（`tests/test_all.sh` 逐条）

### 3.0 公共夹具

脚本一开始 `cd` 到工程根目录并建 `tests/work/`，所有产物都在里面，便于失败后原地复现：

| 变量 | 值 | 含义 |
| --- | --- | --- |
| `SRC` | `tests/work/source.bin` | 4 MiB 随机源（`head -c 4194304 /dev/urandom`） |
| `TOTAL` | `4194304`（4 MiB） | 目标逻辑大小，必须 == `SRC_SIZE`（见 5.3 缺陷-S1） |
| `BLOCK` | `262144`（256 KiB） | 每块大小 |

## 4. 边界与异常用例的设计思路

### 4.1 为什么选 128KB（T5.1）

`SIO_MIN_LOGICAL` 就是 `128*1024`。选它当边界用例有两个理由：

1. **它是作业写死的下限**，也正是最容易被实现成「必须等于 128KB」的地方。我用「恰好 128KB 必须成功、
   64KB 必须失败」把区间卡死：如果实现写成了 `total != SIO_MIN_LOGICAL` 就拒绝，
   T5.1a 会挂；如果下限校验被删掉，T5.2 会挂。
2. **边界处最容易暴露整数与对齐问题**：131072 / 65536 = 2 块整除，没有尾块，
   所以 T5.1 是「干净的整除路径」，与 T5.3 的「非对齐尾块路径」互为对照。
   两条一起跑，才能区分「块数公式整体错」和「只在尾块上错」。

`--head=0` 也是有意为之：它验证「头区块不是必须存在」这条分支（`sio_map_nblocks` 里
`head_size > 0 ? 1 : 0`），保证块数公式在 head 为 0 时不会多算一块。

### 4.2 为什么一定要测非块对齐（T5.3）——它的价值已经被证明

源大小取 `128*1024 + 12345 = 143417`，`--block=64K`，`--head=100`：

- `head=100` **不是** 64K 的整数倍，于是「头区之后的数据」与块边界天然错位；
- 143417 也不是 64K 的整数倍，于是必然存在一个**不满的尾块**；
- 正确块数 = `1 + ceil((143417-100)/65536) = 4`，其中块 3 是 `[131172, 143417)` 共 **12245 字节**的尾块。

这个用例的期望值是我手算的、且用**外部 sha256** 判定的，因此它能抓到内部块数公式的任何偏差。
实测结果是：它抓到了一个真实缺陷（第 5.1 节），**这是整份用例集里价值最高的一条**。
另外注意：如果把这条用例写成「目标 > 源」的变体（比如源 143417、目标却建成 1M），
那测的是另一个分支（exit 4），反而测不到尾块——**边界用例的尺寸必须精确设计，差一个字节就换了被测代码路径。**

### 4.3 为什么测「目标 > 源」（T5.4）

因为这是一种**看上去会成功**的错误：目标 2MiB、源 1MiB 时，逐块读取每块都成功，
程序可以一路「成功」地把前 1MiB 写完，退出码 0，而尾部 1MiB 永远是空洞，
`sha256` 与源完全不同——**日志全绿、数据全错的典型静默失败**。
它检验的是「整体可满足性校验」，而不是「单块读取是否成功」——两者很容易被实现者混为一谈。
断言要求退出码**恰好是 4**（`SIO_ERR_RANGE`），而不是「非 0」，因为 4 才表示「范围不可满足」。

### 4.4 为什么测参数一致性（T5.6）

对同一个目标文件，第一次用 `--block=256K` 建位图并写下 7 块，第二次改用 `--block=128K` 续传。
如果程序不校验，会发生什么：新的块划分把原来的 `[4096, 4096+6×256K)` 重新切成
`[4096, 4096+128K)`、`[4096+128K, …)` 等更细的块，位图里「已完成」的位与新的块编号**语义完全对不上**——
程序会以为某些块已完成而跳过，或把数据写到错的偏移上，最终得到一个「没有任何报错但内容错位」的文件。
所以我要求它**必须拒绝**（退出码 5 = `SIO_ERR_BITMAP`），并在提示里告诉用户改回原参数。
这条是 AI 没想到、我自己补的：它防的不是崩溃，而是**用不同分块策略静默重下把数据写错位**。

### 4.5 为什么「64KB 被拒」要和「未知子命令被拒」放在一起（T5.2 / T5.7）

两者都是参数层错误，都必须回 **2**（`SIO_ERR_USAGE`）。放在一起是为了固定「错误分类」这一契约：
参数错误 → 2，范围不可满足 → 4，位图不一致 → 5。分类一旦被破坏（比如把参数错误也回 1），
脚本的失败信息就会指向错误的方向，排障时间成倍增加。

## 5. 发现缺陷的用例

### 5.1 「非块对齐 + 尾块」用例（T5.3）——抓到块数公式少算 1 块（缺陷-10）

这是本次实测里最严重、也最能说明「测试用例价值」的一个缺陷。

**用例**：`head=100`、`block=64K`、源 = 143417 字节（`128*1024 + 12345`）。

**现象**：`create` + `write` 全部「成功」，退出码 0，日志打印 `全部块提交完成`，
但 `sha256sum` 与源不一致。逐字节比对发现：文件只被写到偏移 **131172**，
尾部 **12245 字节**（`143417 - 131172`）永远是空洞（全 0x00），从来没有被任何一块覆盖过。

**根本原因**：`sio_map_nblocks()` 原来写成
`ceil((total_size - head_size) / block_size)`，把「头区块」当成了数据块里的第 0 块，
于是数据块数量比实际需要**少 1**。偏偏 `sio_map_block_range()` 又是按
「数据块序号 × block_size」递推偏移的，末尾那段不足一块的数据就再也落不到任何块上：

| | 旧公式（错） | 新公式（对） |
| --- | --- | --- |
| 块数 | `ceil((143417-100)/65536) = 3` | `1 + ceil(143317/65536) = 4` |
| 块 0 | `[0, 100)` 头区 | `[0, 100)` 头区 |
| 块 1 | `[100, 65636)` | `[100, 65636)` |
| 块 2 | `[65636, 131172)` | `[65636, 131172)` |
| 块 3 | **不存在** | `[131172, 143417)` 尾块 12245 字节 |
| 实际覆盖到 | 131172 字节 | 143417 字节（完整） |
| 程序报告 | 「全部块提交完成」，退出码 0 | 一致 |

**修法**：数据块按 `(total - head + block_size - 1) / block_size` 计算，
并在头区存在时单独 `+1`；`sio_map_block_range()` 已把 `end` 收在 `total_size` 内，
最后一块自然成为「尾块」（允许不满一块）。

**为什么这个用例不可替代**：

1. 它**只在 `head` 不是 `block` 整数倍时**才暴露。`head=4096` + `block=256K` 的主用例（T1–T4）
   因为 4096 恰好整除 4KiB 分配粒度、且块数足够多，尾部偏差被「最后一块本来就不满」掩盖了，
   **T1–T4 全绿也发现不了它**。
2. 程序**自己报告成功**。没有外部 `sha256` 比对，任何「看日志」的检查方式都会放它过去——
   这正是我在 1.4 节强调「强档断言」的原因。
3. 它属于**静默数据损坏**：用户会拿到一个看似完整、大小正确、但尾部内容全是 0 的文件。

### 5.2 HTTP 源在服务端不支持 Range（返回 200）时的连接残留（缺陷-12）

**现象**：当数据源是一个「忽略 `Range` 头、任何 GET 都回 200 + 整个文件」的服务端时，
下载在第 2 块起开始报 `无法解析状态行: <乱码>`，并伴随大量重连，最终块读取重试耗尽、
以退出码 6（`SIO_ERR_NET`）保留断点退出。

**根本原因**（`src/sio_http.c` 的 200 降级分支）：服务端不支持 Range 时，客户端的降级策略是
「在流里跳过前 `start` 字节」——但这只是**客户端不再读**那一段，
服务端仍然会把整个响应体写进同一个 socket。于是连接里残留着上一次响应没读完的字节，
下一个块的请求就把这些**残留字节当成 HTTP 状态行**来解析，出现乱码并反复重连。

**修复**：走 200 降级路径时给连接打上 `sock_dirty` 标记，**读完整块响应体后立刻 `close()`**，
让下一块重新建连；而 206 分支由 `Content-Length` 精确分隔，仍可安全复用长连接
（这一点很重要：如果为了修这个 bug 把所有连接都关掉，Range 逐块请求就会退化成「每块一次 TCP 握手」，
性能白丢）。同时补了「响应体比请求区间还短就直接报 `SIO_ERR_RANGE`」的提前拦截。

**这条用例的测法与注意点**：`sio_http.c` 里 HTTP 源默认走 **curl 通道**
（`have_curl()` 为真时 `use_curl=1`，由 `curl -r a-b` 保证 Range 语义），
而 200 降级分支属于**内置 socket 实现**。所以要复现它，必须让 `have_curl()` 判定为假
（PATH 里没有 curl）后才会走到那段代码——**这也是为什么这条缺陷没有被 `make test` 抓到：
测试机上有 curl。** 我把它记在这里，并且老实说明它目前只是手工复现，
没有固化成 `test_all.sh` 的断言（否则要为它临时屏蔽 curl，会污染 T1–T4 的运行环境）。

### 5.3 顺带说：测试脚本自己也会写错

写这些用例的过程中，我修掉的**测试侧**缺陷（脚本注释里编号 S1–S7），比被测程序还多。
列出来是因为它们直接印证了第 7 节的局限：

| 编号 | 测试脚本的错误 | 后果 | 修法 |
| --- | --- | --- | --- |
| S1 | `TOTAL` 写成 6MiB，而源只有 4MiB | 下载器**正确地**以「目标 > 源」拒绝（exit 4），T2–T4 连锁失败 | 让 `TOTAL` 与 `SRC_SIZE` 同源，并写明「这属于测试设计缺陷而非程序缺陷」 |
| S2 | 用 `--block=1M` 配 128K 源 | 被程序正确拒绝（exit 2） | 块大小必须 ≤ 总大小，改用 `--block=64K` |
| S4 | `wait $WPID 2>/dev/null; rc=$?` | `wait` 失败会让整个脚本在 make 下报「没有子进程」并中断 T6 段 | 把 `wait` 包在 `if` 里显式捕获退出码 |
| S5 | 断言前忘了 `2>&1` | 下载器日志走 stderr（`sio_util.c` 的 `vlog`），`RESUME_OUT` 为空、解析出 0，误判成「没跳过任何块」 | 所有要正则解析的调用统一 `2>&1` |
| S6 | T3 先跑完整续传再断言 | 文件已是 17/17，只能观察到「跳过 17 块」，**测不到「复用断点、只补剩余」的语义** | 先 `--limit=1` 构造未完成状态，再断言「跳过 7 + 新写入 1 块」 |
| S7 | SIGINT 用例用 `--delay=60` | 17 块在 1.5s 内就跑完了，`kill -INT` 打在已正常退出的进程上，拿到退出码 0 而误判 | `--delay=300`（17 块 ≈ 5.1s > 1.5s），保证发信号时进程仍在下载 |

结论很明显：**一条「失败」的测试未必说明程序错，先怀疑测试自己。** 我后来养成的习惯是，
每次断言失败先手工跑一遍那条命令，确认是程序错了还是我的期望值错了。

## 6. 测试结果

### 6.1 实测结果

测试脚本已经固定住"通过/失败"的判定方式（逐条打印 `[PASS]` / `[FAIL]`，末尾给出通过计数）。

## 7. 测试局限（我认为必须写清楚的部分）

1. **稀疏行为只在 ext4 上实测。** `st_blocks` 在 `tmpfs`/`btrfs`/`zfs` 上的语义不同
   （`btrfs` 的 `st_blocks` 与压缩/CoW 交互，`zfs` 更复杂），客户机只有一个 ext4 根分区，
   无法换文件系统复测。所以 T1.3 / T2.5 的阈值只在 ext4 上被验证过，换文件系统要重新解读。
2. **`st_blocks` 的粒度是 4KiB，空洞占比是「下限估计」。** 只写 1 字节也会体现为 1 个块（4096 字节）的占用。
   因此我把所有占用类断言写成**上界**（`< 64KiB`、`< 已写数据 + 8 块`），而不是等值，
   它们能证明「空洞没有被写实」，但**证明不了字节级精确的占用**。精确进度只能看位图的 `blocks_done/blocks_total`。
3. **T6（SIGINT）是时间依赖用例，天生脆弱。** 它靠 `sleep 1.5` 后发信号，
   而「进程此刻还在下载」依赖 `--delay=300 × 17 块 ≈ 5.1s > 1.5s` 这个时间窗。
   如果哪天有人把 4MiB 源改小、把块数改少，或者机器慢到 1.5 秒内还没开始写第一块，
   这条用例就会变成「偶发失败」——它测的是信号处理，不是性能，所以对时序敏感是它的固有代价。
   （这也是缺陷-S7 的由来：早期用 `--delay=60`，进程 1.5s 内就退出了，`kill` 打空。）
4. **位图原子性没有做故障注入。** 「写位图过程中被杀会不会留下半个位图」这一条，
   我是通过代码论证（写 `.tmp` → `fsync` → `rename` 覆盖，`rename` 同文件系统内原子）
   和目录 `fsync` 的补强来说明的，**没有**真的在写位图的微秒级窗口里 `kill -9`。
   要真正验证需要 `LD_PRELOAD` 注入或内核故障注入，超出这次的环境与时间预算，
   所以它是「设计上正确」而不是「实测过」。
5. **没有覆盖的路径**：`--retry` 的失败重试分支（没有做读写故障注入）、
   多进程/多线程并发写同一目标（作业未要求，位图无跨进程锁）、
   `>2GiB` 的大文件与 `off_t` 溢出边界（虚拟机磁盘与时间都不够）、
   HTTPS（`sio_http.c` 里有 `https` 分支但没接 TLS 库，README 已把它写进已知限制）、
   掉电级别的持久性（只做了 `fsync` 语义层面的论证）。
6. **HTTP 端到端依赖 curl。** `sio_http.c` 在有 curl 时默认走 `curl -r a-b` 通道，
   无 curl 时回退内置 socket 实现——**这两条是两套代码**，而 `make test` 只覆盖了前者能跑通的那条。
   5.2 节的缺陷-12 恰好只在无 curl 的内置实现里出现，因此它没有成为 `test_all.sh` 的断言。
   这是我认为当前测试集最值得补的一块：加一个「把 PATH 缩到最小后重跑 HTTP 用例」的独立分支。
7. **`report.sh` 第 4 步的注释与实测不符。** 那一步用 `python3 -m http.server` 当源，
   注释写「支持 206」，但 `demo.sh` 里的实测备注明确写着 Python 3.10 的 `http.server` 忽略 `Range`、
   任何 GET 都回 200。也就是说 `logs/04_http_range.log` 走的**不是** 206 路径，
   不能拿它当「Range 端到端」的证据；真正的 206 证据来自 `make demo`（用的是自写的 `range_server.py`）。
   我把这一点留在这里而不是悄悄改掉注释，因为它正好说明**测试证据也要核对来源**。
8. **断言数量不等于覆盖率。** 29 条断言里有 3 条是 `ok/bad` 风格的条件分支
   （T2.3、T5.5 等），它们和等值断言在信息量上并不等价；
   29 这个数字只说明「脚本跑完了 29 个检查点」，不能说「程序 100% 正确」。
   真正让我放心的不是这个数字，而是第 5 节里那两条用例——**它们证明这套测试确实能抓到真缺陷。**

## 附：我认为「AI 辅助测试」这件事的真实结论

- **AI 最有用的一次**是 Prompt 2 里那句「重点想什么输入会让它悄悄出错但看日志又是成功的」——
  它逼我把注意力从「测功能有没有」转到「测数据对不对」，直接催生了 T5.3 和 T5.4，
  而 T5.3 就是那个抓到尾块丢失的用例。
- **AI 最没用的一次**是 Prompt 4 里建议的真实公网源和 `LD_PRELOAD` 故障注入：
  方向都对，但在「可复现」和「本次环境预算」两条约束下都得砍掉。
- **AI 一定做不了的事**：给断言定期望值。AI 会写 `assert 退出码 == 0`，
  但「尾块应该是 12245 字节」「总块数应该是 17」这种数字，必须我自己按公式算、再拿外部工具交叉验证。
  期望值一旦来自被测程序，用例就自动变成永远通过的空壳。
